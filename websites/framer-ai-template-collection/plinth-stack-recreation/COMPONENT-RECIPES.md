# Plinth Stack — five component recipes

These authored recipes use official images and public homepage/Trust Center declarations. Typography is declared, spacing is recommended, and interactions were not tested.

## 1. Paper hero and request triptych

Center the headline above a dark console with a painted wash behind the opening. Add a mono eyebrow, install pill, and four compact metrics. The console reads left to right as request, router, response, separated by rules. Preserve selected-model and rejected-model reasoning. Hero typography declares Schibsted Grotesk Variable at 78px, weight 400, with axes wght 600 and opsz 72. Keep these distinct. Use cobalt emphasis on one meaningful word. On phones, stack request, model choice, and response in that order; long code needs scrolling and accessible wrapping controls.

## 2. Narrative and evidence pairs

Build Inference, Evals, and Observability as alternating explanation/interface pairs. Include eyebrow, heading, paragraph, capability rows, and documentation or pricing action. Interfaces use real text, thin separators, mono metadata, and specific evidence: eligibility table, failed evaluation gate, or spend breakdown. Source Wrap rules declare a 50.4px gap and change to column on tablet/phone. Recommend similar breathing room with variable content height. State whether data is demo, delayed, or live and retain useful headings when values are unavailable.

## 3. Six-stage request architecture

Create six lifecycle steps paired with a diagram using matching labels. Give each step an index, name, and description; keep retention context with recording. Source scroll markers and graphical paths were not tested together. Recommend a complete static diagram with optional current-step highlighting. Every stage should remain keyboard-inspectable and visible without scrolling effects. On phones, use a vertical stage list. Product latency numbers and region behavior need actual measured deployment information rather than example narrative.

## 4. Security and Trust Center disclosure

Place the homepage security section after benchmarks so buyers can examine both product evidence and data controls. Carry its trust link to a separate disclosure route with commitment, certifications, retention, sub-processors, controls, and closing-contact sections. Keep placeholder chips visibly attached to unauthenticated certification badges. Recommend status labels such as placeholder, planned, in review, and verified, each with evidence date and scope. Avoid making a generic badge look earned by hiding its caveat in a tooltip. The trust page's data-training commitment is demonstration copy and needs product approval before reuse. On small screens, turn disclosure tables into clearly labeled rows while preserving columns' meaning.

## 5. Quickstart, pricing path, and proof cards

Use Quickstart as a compact bridge from explanation to implementation, with editable syntax-colored code, language choice, copy control, and a documentation action. Code must be visibly labeled as example until it matches the real API. Keep customer stories and metrics marked illustrative. The official pricing image shows a calculator with input/output token sliders and a dark monthly-fee summary; this belongs to the pricing route, not the homepage. An authored calculator must expose rates, units, rounding, exclusions, and stale-price state. Do not let estimates imply a purchase. Finish with changelog, FAQ, CTA, and comprehensive footer links so the evaluation path remains available after the narrative.
