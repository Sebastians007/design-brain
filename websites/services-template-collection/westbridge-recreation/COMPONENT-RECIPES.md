# Westbridge component recipes

Evidence comes from the public preview HTML/CSS and official promotional references. CSS values below are declarations, not rendered measurements. Device hardware in the references is presentation scenery. Recommendations are explicitly optional.

## 1. Portrait hero and transparent navigation

**SOURCE DECLARED:** Build an image-backed hero using the Westbridge portrait JPEG, not a video. The source declares a viewport-height hero and a 1920px maximum content width. Place the logo and navigation over the image, with a pale contact action at the right. A report pill precedes the overview and partner action; the display statement sits lower. Sentient 300 at 76px/83.6px, with −0.05em tracking, establishes the desktop title. Its nested spans override the dark parent color with pale and muted tones. Lateral and bottom gradients protect the text. **OPTIONAL:** Retain a readable image crop at shorter heights and test the photograph’s right-side subject position. Add an accessible menu trigger and visible focus treatment.

## 2. Introduction and metric strip

**SOURCE DECLARED:** Follow the hero with the welcome section, including a small label, introduction, contact action and four metric units. Figures use Sentient 300 at 62px/80.6px; captions use TASA Orbiter 400 at 14px/18.2px with tight tracking. The source distinguishes desktop and mobile metric structures. Some inline spans start almost transparent and slightly translated, which documents reveal preparation without proving the eventual effect. **OPTIONAL:** Make a reusable figure/caption pair with a semantic list wrapper. Keep values as editable content, allow captions to wrap and present the final readable state when motion is reduced. Treat template metrics as demonstration content requiring client approval.

## 3. Expertise service cards

**SOURCE DECLARED:** The expertise section combines a small label, two-tone serif heading, overview and partner action with three linked services: M&A Advisory, Performance and Growth. Each has its own image, a Sentient service title and a TASA Orbiter subtitle. Actual routes identify individual service pages. Default and Hover In variants appear in the component structure; desktop, tablet and mobile versions exist. **OPTIONAL:** Recreate each entire card as one focusable link, with an arrow suffix and sufficient target size. Preserve the image/title/subtitle association during stacking. Mirror any hover emphasis with keyboard focus rather than making the image the sole interactive cue.

## 4. Dark approach presentation

**SOURCE DECLARED:** A dark section introduces the approach with light typography and an About Us action. Its feature-carousel structure contains three numbered tabs, active/inactive variants, a progress-animation element, image panels and outcome metrics. Desktop, tablet and mobile structures differ; narrow variants include additional descriptions. Panel headings use the 32px Sentient role. **OPTIONAL:** Implement this as accessible tabs only after selecting interaction requirements. Keep panel imagery, outcome and explanation together; announce selection and support arrow keys. An optional restrained transition can connect states, while reduced motion removes progress animation. Static evidence does not establish automatic rotation, swipe support or duration.

## 5. Proof, briefing and conversion footer

**SOURCE DECLARED:** Client-success content follows the approach, then an insights section, then the footer. Proof combines testimonial imagery, attribution, a case-studies action and three outcomes. A Play affordance exists, but the captured document exposes no video element. Editorial cards carry category, date, image, title and excerpt. The footer combines a business CTA, route columns, social links and a required email subscription field. **OPTIONAL:** Reuse article-card data without duplicating responsive content in the accessibility tree. Add explicit labels and accessible submission feedback to the subscription form. Connect playback or submission only to verified destinations; keep success/error states separate from assumed backend behavior.
