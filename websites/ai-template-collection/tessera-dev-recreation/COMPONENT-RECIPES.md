# Tessera Dev — five component recipes

Evidence basis: official marketplace imagery and public preview HTML/CSS. The source supplies visual and structural declarations. Every implementation choice below is a recommendation; interactions and backend services were not exercised.

## 1. Serif schema hero and mosaic table

Use the source split composition: install chip, serif statement, lede and paired actions on the left; a rounded database scene over a peach wash on the right. Preserve Newsreader's normal first phrase and italic emphasis, using actual emphasis markup rather than a slanted transform. The public hero stage declares a 1200px maximum and 600px height at its base. For a recreation, express the schema graphic as deterministic tile data with column labels and accessible explanatory text. Keep a static initial table available. Avoid presenting simulated rows as a connected database. Copy-command feedback should distinguish success from clipboard failure.

## 2. Four-stage workflow demonstrator

The declared workflow organizes schema, data, query and live stages in one pale sage enclosure, with code/table imagery and thin progress tracks. Build a reusable stage record containing label, explanation, code text, illustration and accessible status. Selecting a stage should replace only the demonstration panel and keep the surrounding section stable. Recommendation: allow arrow-key selection and provide explicit previous/next buttons on small screens. Autoplay, if added, must pause when a visitor makes a selection or requests reduced motion. Keep sample code selectable. Treat migration safety and realtime claims as authored marketing examples until a real product substantiates them.

## 3. Customer proof and community window

Retain the distinction between curated customer cards and the smaller community-post region below them. The source declares portraits, company artwork, quotation, attribution and a separate post window; those records should not be flattened into one generic review carousel. For reconstruction, use typed customer and community records with optional image, role, timestamp and destination fields. Preserve the restrained blush tint and quiet border hierarchy. Make card links independently focusable without turning quotation text into a giant ambiguous target. Supply image alternatives and reserve portrait space before loading. Replace fictional customer metrics with approved evidence when adapting this visual system for a real launch.

## 4. Platform tabs with code mock

The source declares five platform tabs above an explanatory panel and code mock, followed by four capability benefits. Use one shared tab component with active, inactive, focus and disabled states, and associate each tab with one labelled panel. Recommendation: distinguish tab selection from a navigational link, keep keyboard focus on the chosen tab and announce the panel heading. Maintain monospace code alignment without forcing the entire page to overflow. On phones, use a horizontally scrollable tab rail with a visible selection indicator. The displayed schema and API examples belong to a demonstration dataset; neither the tab panel nor an animated response proves endpoint execution.

## 5. Release feed and marching conversion scene

Build release entries and editorial posts from separate records, sharing spacing and metadata styles while retaining distinct fields. Releases need version, date, kind and summary; articles need category, date, title, excerpt and destination. Follow the source with a final conversion panel and repeated install chip before the multi-column footer. Reuse the four-tile motif for its marching visual, keeping decoration outside the reading and focus order. Recommendation: a static tile arrangement should be the reduced-motion state. Validate missing article routes, unavailable commands and empty feeds explicitly. Keep footer product, developer and company destinations intact rather than replacing the information architecture with a single newsletter block.
