## OPTIONAL PRODUCT ADAPTATION

Position the product around a bounded conversational task: helping a visitor turn a rough request into a useful next step. Author a hero that names that task, then use the three capability cards to show drafting, summarizing and planning. Keep the four use cases meaningfully distinct by changing the input, expected output and evidence shown, rather than merely swapping illustrations.

A recommended demo is a contained example conversation inside the selected use-case panel. Offer three prepared prompts and a reset action. Label the transcript as a demonstration. If no model service is connected, provide authored sample responses and make that state visible. A functional version should distinguish ready, submitting, generating, completed, interrupted, failed and input-too-long states; announce progress without continuously reading streamed text aloud. Let users copy or refine an output, and make retry available after failure.

Replace broad trust language with specific, supportable disclosures: available models, input retention, account scope, deletion controls and any limits on uploaded material. Place relevant details near the demo and plan table as well as in FAQ. Show assistant uncertainty through a short request for missing context or an explicit limitation, rather than an invented certainty score.

Preserve the quiet visual character when adding these states. Use short labels, restrained outlines and readable contrast instead of animated intelligence metaphors. Before launch, verify keyboard selection, disclosure behavior, mobile navigation, billing copy, external destinations and the actual connected assistant independently; this reference inspection did not test them.
